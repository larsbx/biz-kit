# Cluster

Date: 2026-10-19. Status: **implemented**. Lets biz-kit run on several nodes
behind a load balancer. Before this, sessions, held commands, enrolment
requests, feed nonces and rate-limit counts lived in each node's memory, and
the ledger's appender kept its head and gate in one node's process.

## Decision

The nodes form one **distributed Erlang cluster**, and everything that must
be one for the service runs **once per cluster**:

| Process | Holds | Was |
| --- | --- | --- |
| `CoopSubstrate.Log` | the appender: head and gate | one per node, unsafe on two |
| `CoopSubstrate.Commands` | envelopes held for signing | per node |
| `CoopSubstrate.Enrolments` | challenges, requests, codes | per node |
| `CoopSubstrate.Feed.Nonces` | spent signed-read nonces | per node |
| `BizKit.Identity.Sessions` | sign-in sessions | per node |
| `SpruceGoose.Web.RateLimit.Counts` | request counts | per node |

Each runs under `BizKit.Cluster.Singleton` (new app `biz_kit_cluster`):

- **Keepers.** Every node supervises a keeper. The first to register the
  module's name in `:global` starts the process; the others monitor it.
  When it goes, because its node stopped or became unreachable, they race to
  start it again.
- **Calls.** Every call goes to it by name from any node:
  `GenServer.call(Singleton.name(module), ...)`.
- **Partitions.** When a partition heals with one on each side, the copy on
  the lower-named node stays. The other stops with
  `{:global_name_conflict, module}`, and its keeper then watches the
  survivor.

**Feed notifications** use `:pg` (group `:ledger` in scope
`CoopSubstrate.Feed`, started on every node). The appender, wherever it
runs, notifies every node's feed sessions after each append, in ledger
order.

**Joining.** Nodes connect to each other through `BizKit.Cluster`, which
keeps trying every peer in `BIZKIT_CLUSTER_NODES`. Each node also needs
`RELEASE_DISTRIBUTION=name`, its own `RELEASE_NODE` and the cluster's
shared `RELEASE_COOKIE`. A node with no peers is a cluster of one, which is
what development and the test suites run.

No new store, registry or authorization system: the ledger stays the
Postgres event store, and the stores stay in memory, now one per cluster.

## The ledger cannot fork

Only one appender should run, but during a partition each side may start
its own. The event store's expected-version check still admits only one of
them per position:

- the second appender's append is refused with `wrong_expected_version`;
- that appender stops (`:ledger_moved`), and its keeper starts it again,
  from the store, with the other's events included.

The chain stays linear, and `Log.verify_chains/0` holds.

## What moving costs

A singleton's in-memory state is lost when it moves, as it was on a
restart:

| Lost | Effect |
| --- | --- |
| sessions | everyone signs in again (fails closed) |
| held commands | prepare again |
| pending enrolment requests | the device asks again |
| spent nonces | a signed read could be replayed once more within its 60 s window |
| rate counts | counting restarts |

The appender loses nothing: it rebuilds from the store.

## Costs and limits

- Every use is a call to one process, often on another node.
  - `Log.gate/0` copies the gate to the caller's node.
  - Each request's rate count is one call.
  - This is fine at today's size. If it stops being fine, the remedy is to
    cache the gate per node behind the feed's notifications, not another
    store.
- `:global` with `prevent_overlapping_partitions` (OTP's default) cuts a
  node off from everyone when it loses one peer, so a flaky link moves
  singletons. Run the nodes on a reliable network.
- Partitions are resolved by OTP. During one, each side has its own
  sessions and stores, and only one side's appends reach the ledger.

## Verification

- **`BizKit.Cluster.SingletonTest`** (real peer nodes via `:peer`):
  - one instance, reached the same from every node;
  - when its node stops, another takes over;
  - after a partition heals, one remains, on the lower-named node.
- **`CoopSubstrate.ClusterTest`**: a peer node that runs none of the
  processes itself
  - appends through the one appender;
  - proves, fetches and approves an enrolment whose request and approval
    were held on another node;
  - spends a nonce that is then spent here;
  - hears every append through `:pg`.
- **The ledger cannot fork:** a second appender moves the ledger; the stale
  one is refused, restarts from the store, appends again, and the chains
  verify. Removing the step-down fails this test.
- **`BizKit.Identity.ClusterSessionsTest`:** a session issued on one node
  works on another, and revoking it there ends it here.
- **Existing suites:** every existing suite passes unchanged against the
  singletons.
