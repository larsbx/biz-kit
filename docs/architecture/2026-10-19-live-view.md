# The view follows the ledger

Date: 2026-10-19. Status: **implemented**. Closes the limits that left parts
of the web view stale or polling:

| Part of the view | Before | Now |
| --- | --- | --- |
| a device's enrolment and the person's device list | asked every 30 s (10 s while a request was pending) | updated when the project's feed says the person's devices changed |
| **Projects of this chapter** | read on load and after the administrator's own acts ([chapter projects](2026-10-19-chapter-projects.md#limits)) | the chapter's feed |
| **Administrators of this chapter** | read on load and after the administrator's own acts | the chapter's feed |
| **A person in this chapter** | read on lookup and after the administrator's own acts | read again on every frame of the chapter's feed |

## Decision

The change feed ([change feed](2026-10-18-change-feed.md)) already pushes
every change to a project's tasks and suggestions. It now carries the rest
of what the page shows, and the page reacts to its frames instead of asking
again. The delivery contract is unchanged: one session per reader, a frame
per batch that changes the view, a cursor to resume from, revocation ending
the stream. It is still the contract `spec/change_feed.qnt` checks, since
that model is about delivery, not about what a view holds.

## A project's view: the reader's own devices

`Feed.View.select/3` takes the reader's principal. A project's view gains
the kind **devices**: that principal's active operator and reviewer grants
in the project, and the governance keys of the chapter declared for them.
These are exactly `Devices.list/2` (now `Devices.of/3`, pure).

| Kind | Key | Fields |
| --- | --- | --- |
| device | grant event ID, or the key ID of an administrator key | `kind` (`operator`, `reviewer`, `administrator`), `grant_id`, `key_id`, `label` |

- Only the reader's own devices are in the view. Another person's never
  appear, and a session without a reader (trusted in-process callers) has
  none.
- The page re-reads its enrolment status, one request per role, only when a
  frame changes **devices**: granted, revoked, or an administrator key
  declared or revoked, here or anywhere else. The list itself comes from
  the view.
- Polling remains only while there is no feed to say anything. A person who
  holds nothing in the project cannot read its feed, so their first request
  is still checked every ten seconds while pending. When the feed refuses
  the page (its last access revoked), the page empties its view, starts over
  from cursor 0, and goes back to asking until access returns.

## A chapter's view, for its administrators

```
GET /api/v1/chapters/:chapter_id/feed      (server-sent events, session only)
```

The scope is `{chapter}`. The reader is a person signed in who holds a
governance key of the chapter declared for them
(`Access.for_administrator/3`, now for any scope of the chapter). The stream
ends when the key is revoked, as a project's ends when a grant is, or when
it comes to name someone else (revoked and declared again in one batch). A signed
read (an agent's) names a project, so it is refused here.

| Kind | Key | Fields |
| --- | --- | --- |
| project | `tenant/project`, each part URI-encoded | `tenant_id`, `project_id`, `tasks` (by state), `grants`, `people` |
| administrator | key ID | `principal_id` (none for a key declared without one) |

`grants` is new in `Administrators.projects/2`: the project's active grants
and delegations. It makes any change in access a change in the project,
even one that leaves the same people (one of two devices revoked). That
change is what tells the page to read the person it shows again.

## The page

- The project's feed builds the view. On a frame that changes **devices**,
  the page asks where this device stands. Becoming an administrator opens
  the chapter's feed, and ceasing to be one closes it.
- The chapter's feed renders **Projects** and **Administrators**, and shows
  again the person the administrator looked up, if any.
- The page no longer re-reads after its own acts. Approving, cancelling,
  revoking or offboarding comes back as a frame like anyone else's change.
  The one exception is the person shown, read again after an act on them,
  so their buttons are ready once the decision ends.
- `GET …/devices`, `GET …/projects` and `GET …/administrators` stay as they
  are, for scripts.

## Verification

- **`LiveViewTest`:**
  - a project's feed carries its reader's devices as they are granted and
    revoked, and never another person's;
  - an administrator key is among its holder's devices in every project of
    the chapter;
  - a chapter's feed is refused to non-administrators;
  - it carries projects and administrators, and changes with a project's
    tasks;
  - it changes with access that leaves the same people;
  - it ends when the reader's key is revoked, or is declared again for
    someone else;
  - a project reader cannot open it.
- **`ChangeFeedViewTest`:** every existing property holds for a project's
  view without a reader, for Alice's view (with her devices), and for the
  chapter's view:
  - applying frames reproduces the view however events are batched;
  - a frame changes only what changed, each entity once;
  - frames encode as JSON, with no signing key in them;
  - other scopes stay empty.

  The coverage test now expects all seven kinds.
- **HTTP:**
  - `AdministrationTest`: the chapter's feed is refused before the person is
    an administrator, then streams the projects and a task created in
    another project. A signed read is refused.
  - `FeedTest`, `AuthTest`: a reader's first frame now holds their device.
- **Node:** frames of any kind, devices in order, and the chapter's lists
  sorted.
- **Browser (Chromium):**
  - the administrator's projects card shows the person's completion,
    signed in another browser, within 5 s, with no reload;
  - after the offboarding, the reviewer's own page drops its device and its
    review controls within 5 s;
  - with the previous page code (re-reading only after its own acts), the
    first of these fails.

## Limits

- A device with no access yet still checks its request every ten seconds.
  It reads nothing from the ledger until something is granted to it.
- An enrolment code's expiry is not a ledger event. A pending code is shown
  until the next status read.
- Each feed session folds the ledger on open, as before
  ([change feed](2026-10-18-change-feed.md#limits)). An administrator's page
  now holds two sessions: the project's and the chapter's.
