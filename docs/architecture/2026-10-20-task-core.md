# A task core any application can vendor

Date: 2026-10-20. Status: **implemented (first stage)**.

Task and workflow management is no longer only biz-kit's. School operations
and other applications need the same rules. Here, a lesson is a task, a
prerequisite lesson is a predecessor, an assessment is a Definition of Done,
a learner's work is evidence, and marking is a review. `apps/task_core` holds
those rules as an umbrella app with no dependencies. A host vendors it as a
git or path dependency and supplies its own storage, signing and transport.

## What is in it

| Module | What it is | From |
| --- | --- | --- |
| `TaskCore.Lifecycle` | A versioned, finite, fail-closed state-machine contract, verified when a declaration compiles. `violations/1` decides reachability and termination over the whole relation. | SpruceGoose's `SpruceGoose.Lifecycle`, unchanged |
| `TaskCore.TaskLifecycle` | A task's states and moves, as the signed ledger admits them | new: the relation the ledger's commands already enforced, declared once |
| `TaskCore.Dag` | A workflow's dependency graph: unique IDs, no self, unknown or duplicate dependencies, no cycles; a deterministic topological order | SpruceGoose's `Workflows.Dag`, for any map or struct |
| `TaskCore.Admission` | The task event catalogue, and whether one event may be appended | the ledger's `CoopSubstrate.Tasks` |
| `TaskCore.State` | The pure fold of accepted events | `CoopSubstrate.Projections.Tasks` |
| `TaskCore.Readiness`, `DoD`, `Timing`, `Delegation` | Per-domain rules: readiness and execution, the Definition of Done, timing and suggestions, delegation | `CoopSubstrate.Tasks.*` |
| `TaskCore.Steps`, `Decisions` | The command a person signs for a step or for a decision on a suggestion | `CoopSubstrate.Tasks.Lifecycle`, `Decisions` |
| `TaskCore.Host`, `TaskCore.Event` | The port a host implements, and the event shape the rules read | new |

The Quint models of the lifecycle, readiness, cancellation and suggestions
moved with the rules to `apps/task_core/spec`, together with `check.sh`. The
ledger's own model, the change feed, stays in `apps/coop_substrate/spec`. It
is checked by the same script.

## The boundary: pure rules, two ports

The rules read plain data. An event is any map or struct with `event_id`,
`chapter_id`, `type`, `payload` and `signers` (`TaskCore.Event` or the
ledger's envelope). The rules match fields, never a struct. Admission takes
the state and the governance keys:

```
Admission.check(event, %{orchestration: state, role_keys: keys}) :: :ok | {:error, reason}
State.handle_event(event, state) :: state
```

The rules need two effects. The host supplies them through `TaskCore.Host`,
and the state carries the host from `State.init(host)` onward:

| Callback | Used for |
| --- | --- |
| `verify_artifact(digest, limit)` | Admission: are custody, input, SOP and evidence bytes in the store, intact and within the limit? |
| `hash(term)` | The fold: a Definition of Done is named by the canonical hash of its criteria, so replay recomputes it. |

The host keeps everything else:
- verifying signatures;
- serializing admission, so that check and append see the same state;
- storing and ordering events;
- answering a retried command.

The rules assume all of this: they check what a signature authorizes, not
whether it verifies.

## The ledger as the first host

`CoopSubstrate.TaskHost` implements the port with the custody store
(`Harness.Artifacts.verify/2`) and the canonical profile's hash
(`Canonical.hash!/1`). `CoopSubstrate.Projections.Tasks` is the
`TaskCore.State` projection under that host, so the gate and replay still
share one fold.

`CoopSubstrate.Tasks` keeps the ledger's side of task commands:
- `propose/2` and `submit/2` append through `Log`;
- `duplicate/2` answers a retried command;
- the type registry, validity and the gate read the catalogue and the
  checks from `TaskCore.Admission`.

No admission rule, event type, payload or canonical byte changed. The
ledger's 563 tests pass unchanged. The only edits are module names and the
direct `DoD.submit/1` call, which became `Tasks.submit/1`.

## One lifecycle, declared once

Before this change, the ledger's moves were literal state lists in each
command check. They are now one table in `TaskCore.Readiness`
(`moves/0`), with an entry for each command:

| Command | From | To |
| --- | --- | --- |
| `TaskProposedV1` | inbox | proposed |
| `TaskQueuedV1` | proposed | queued |
| `TaskReadyV1` | queued | ready |
| `TaskStartedV1` | ready | in_progress |
| `TaskCompletedV1` | in_progress | completed |
| `TaskCancelledV1` (operator) | inbox, proposed, queued, ready | cancelled |
| `TaskCancelledByGovernanceV1` | inbox … in_progress | cancelled |
| `TaskReopenedV1` | in_progress | queued |

Two checks tie the table to `TaskCore.TaskLifecycle`:
- **When `Readiness` compiles:** compilation fails if an entry is not in the relation.
- **`TaskLifecycleMovesTest`:** the entries together are exactly the relation.

Refusals keep their shape: `{:invalid_task_transition, from, to}`.

SpruceGoose's Ash task and deployment lifecycles now declare on the same
contract (`use TaskCore.Lifecycle`). Its workflow definitions validate
through `TaskCore.Dag`.

### Where SpruceGoose and the ledger differ, the ledger stands

The two task relations stay separate declarations on the shared contract.
These differences are deliberate:

| | SpruceGoose (`Workflows.Lifecycle`) | Ledger (`TaskCore.TaskLifecycle`) |
| --- | --- | --- |
| States | adds `waiting`, `blocked`, `failed` | none of these |
| Reopening | none; `failed → queued` instead | `in_progress → queued`, with a reason |
| Predecessors | checked on entering `in_progress` | checked before `ready` |
| SOP | versioned: grandfathering, `MAJOR.MINOR` compatibility, no rollback | the exact digest governance declared per task |

The task core takes the ledger's side on each. SpruceGoose's relation, its
`SopGate` and its Ash resources are unchanged, and stay where the
consolidation plan puts them ([one source of truth](2026-10-11-single-source-of-truth.md)).

## Vendoring

```elixir
# mix.exs of the host application
{:task_core, git: "https://github.com/larsbx/biz-kit.git", sparse: "apps/task_core", ref: "<commit>"}
```

A standalone Mix project depending on `apps/task_core` by path compiles and
runs it. The host then:

1. implements `TaskCore.Host`;
2. folds accepted events with `TaskCore.State.init(host)` and `handle_event/2`;
3. checks each event with `TaskCore.Admission.check/2` before storing it,
   under its own serialization;
4. builds what a person signs with `TaskCore.Steps.command/4` and
   `TaskCore.Decisions.command/4`.

## Verification

- **`task_core` (30 tests):**
  - **The contract:** closure, sinks, reachability, termination, one relation behind `transition`/`allowed?`/`allowed_from`, and parsing. Checked for the task lifecycle and a lifecycle whose finished states can still move. Also: declaration refusals, and `violations/1` naming an unreachable state and one that cannot finish.
  - **The DAG:** order, ties broken by ID, structs and string keys, every refusal.
  - **`LessonWorkflowTest`:** a school host kept in memory: a map for a store, and no signatures. Two lessons, the second waiting on the first. The test takes one lesson from the inbox through readiness, start, evidence, review and completion, and checks that the second can be readied only after that. It also refuses evidence the store lacks, and refuses completion from `ready`.
- **Ledger (563 tests):** unchanged and passing, plus `TaskLifecycleMovesTest`.
- **SpruceGoose (579 tests):** passing. Its lifecycle test keeps its own relation's assertions; the contract's generic properties are tested once, in `task_core`.
- **Quint:** `apps/task_core/spec/check.sh` and `apps/coop_substrate/spec/check.sh` (both in CI).

## Limits and next stages

- **Biz-kit's vocabulary remains:**
  - `chapter_id` is the root of scope, and `tenant_id`/`project_id` sit below it;
  - an event spec still names its stream and disclosure class, which other hosts ignore.
- **No hierarchy or blueprints yet.** SpruceGoose's Project → Roadmap → Workflow → Task and its git-pinned blueprints are the next candidate: pure data and checks, without Ash. A curriculum in git would then become a workflow.
- **Admission is not a single entry point for every type.** `Admission.check/2` dispatches by type, and a host must route only task event types to it (`Admission.event_types/0`).
- **No cycle check across tasks on the ledger.** `TaskCore.Dag` validates whole workflow definitions. The ledger's per-task predecessor lists are checked as before, so a cycle there leaves its tasks unable ever to become ready; it is not refused.
