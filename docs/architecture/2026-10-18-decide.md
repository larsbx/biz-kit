# Deciding on suggestions: device keys, commands and the web view

Date: 2026-10-18. Status: **implemented**. This is the first end-to-end
workflow:

> An agent suggests a task change, a person reviews it, and the authorised
> decision appears everywhere.

Builds on the [change feed](2026-10-18-change-feed.md),
[identity](2026-10-18-identity.md) and
[task timing and suggestions](2026-10-18-task-timing-and-suggestions.md).

## The rule

A person's decision is a ledger command signed with **their own key**, held
by their device. A sign-in session can read; it cannot sign. The server
prepares the command and checks it against the ledger, but holds no key, and
the ledger admits the command only with the device's signature under the
person's operator grant. No server signs in a person's name.

## Device keys

The web view creates an Ed25519 key pair with WebCrypto, marked
non-extractable: scripts can use the private key but never read it, and it
stays in the browser (IndexedDB). The page shows the public key and its key ID
(`k-` and the first four bytes in hex). An administrator enrols the device by
issuing the person's `TaskOperatorGrantedV1` with that key. A person with
several devices has one grant per device key. Losing a device means revoking
its grant. The Tauri app can keep its key in the OS keychain the same way.

## Commands (CoopSubstrate)

`CoopSubstrate.Tasks.Decisions` turns a decision into the command an
operator signs:

| Decision | Command | Taken from the suggestion |
| --- | --- | --- |
| accept a timing suggestion | `TaskTimingRevisedV1` | the timing, unchanged; `expected_timing_version` is the task's current one |
| accept a create suggestion | `TaskCreatedV1` | title, timing, description |
| decline | `TaskSuggestionDeclinedV1` | (the reason is the person's) |

All three cite `suggestion_event_id`. Accepting copies the suggested body
exactly, so the ledger records it as `accepted`.

`CoopSubstrate.Commands`:

1. `prepare(principal, key_id, scope, decision)` finds the principal's
   active operator grant for that key and project (`:no_operator_grant`),
   requires the suggestion to be pending in that project
   (`:unknown_suggestion`, `:suggestion_not_pending`), builds the envelope
   and checks it against the ledger's current state. It returns the exact
   bytes to sign and holds the envelope for five minutes, bound to the
   principal.
2. `submit(principal, id, signature)` takes the held envelope (once, and
   only for its own principal; anyone else's attempt leaves it untouched),
   attaches the signature, which must verify under the grant's key
   (`{:invalid_signature, _}`), and appends. The ledger then applies all its
   usual checks. A task changed after preparing is refused as stale.

Held commands live in one node's memory, like sessions.

## HTTP (SpruceGoose)

```
POST /api/v1/chapters/:c/tenants/:t/projects/:p/commands
     {"decision": "accept"|"decline", "suggestion_event_id", "reason"?, "key_id"}
     → 201 {id, type, payload, signing_bytes (base64url), expires_at}
POST /api/v1/commands/:id   {"signature": base64url}
     → 201 {event_id, global_seq}
GET  /auth/me → {principal}
GET  /app?chapter=…&tenant=…&project=…   the web view
```

Both POSTs need the session cookie and `application/json`. A cross-site form
cannot send JSON, and the SameSite=Lax cookie is not sent on cross-site
POSTs. Errors: `401` (no session), `403 no_operator_grant`, `400` (malformed),
`404 unknown_command`, `422 invalid_signature`, `409` (the suggestion or the
ledger refused).

## The web view

`/app` is static HTML and three small ES modules, served with a strict
content security policy (`script-src 'self'`).

- `cbor.js` decodes the ledger's canonical encoding (a strict CBOR subset).
  The page decodes the bytes it is asked to sign, and **refuses to sign**
  unless they name this device's key, the expected command type and the
  chosen suggestion. The person confirms the decoded command, not the
  server's description of it.
- `device.js` holds the device key, as above.
- `view.js` applies feed frames. The feed is followed with `EventSource`. An
  error response, such as a `401` before the device's grant exists, closes an
  `EventSource` for good, so the page reopens the feed with backoff from the
  last cursor. A person granted access while the page is open needs no
  reload.

Rendering uses `textContent` only, never HTML from data.

## Verification

- `CommandsTest` (ledger): accepting a timing suggestion and a create
  suggestion, declining with a reason; refusals before signing (no grant for
  that principal, key or project; revoked grant; unknown or resolved
  suggestion) and at submission (another key's signature, which also spends
  the command; another principal or an expired command, neither of which
  spends it; a task changed since preparing).
- `SpruceGoose.Web.CommandTest`: the same over HTTP, plus `/auth/me`,
  missing session, non-JSON bodies, another person's held command, and the
  web view's files and CSP.
- `test/js/app.test.mjs` (Node): the decoder reproduces every committed
  canonical vector and refuses what the profile forbids; **WebCrypto's
  Ed25519 signatures equal the ledger's vector signatures byte for byte**, so
  what the browser signs is what the ledger verifies.
- `SpruceGoose.Web.BrowserTest` (Chromium via Playwright):
  1. A person signs in, and the page makes its device key.
  2. The test enrols that key in an operator grant, and an agent suggests.
  3. The suggestion appears live, the person accepts, the page decodes and
     signs, and the ledger records the decision.
  4. The test checks the decision names the person's principal and grant and
     is signed by the key the browser made.

  CI runs it.
- Mutation: taking a held command before checking its principal, which lets
  anyone spend it, fails `CommandsTest`.
