# Uploads from the browser

Date: 2026-10-19. Status: **implemented**. Follows
[lifecycle steps in the view](2026-10-19-lifecycle.md).

## Decision

A task waiting for a stored copy of its SOP, or of a required input, now
offers **Upload…**. The person chooses the file. The device:

1. hashes it with SHA-256 (WebCrypto), and refuses it unless the digest is
   the one the task names;
2. sends the bytes with that digest to the server, which stores them;
3. signs `ArtifactCustodyRecordedV1` for the digest, through the same
   decode, check and confirm as any command.

The page signs only if the prepared command names exactly the digest it
computed. The ledger admits custody only once the bytes are in the store
and hash to the digest, so custody always covers the file the person chose.
The task's next step (acknowledge, queue, mark ready) then cites the new
receipt as before.

Only what a task names can be stored: the SOP's digest or a required
input's, as some task's readiness in the project defines them. The server
enforces this, not only the view, so a device grant is no licence to store
arbitrary bytes; storage stays bounded by what governance has defined.

## Storing

```
POST /api/v1/chapters/:c/tenants/:t/projects/:p/artifacts   (session)
     content-type: application/octet-stream
     x-content-sha256: <hex SHA-256 computed on the device>
     <bytes>
     → 201 {digest, size}
```

`CoopSubstrate.ArtifactCustody.store/4` decides:

| Check | Refusal |
| --- | --- |
| an active device grant in the project, checked before any byte is read | 403 `no_operator_grant` |
| the claimed digest is a task's SOP or required input here, checked before any byte is read (`may_store/3`) | 422 `not_named` |
| at most 8 MiB, the most a custody receipt covers; more is not buffered whole | 413 `too_large` |
| the bytes hash to the claimed digest | 422 `digest_mismatch` |

Storage is `Harness.Artifacts`, content-addressed, so the same bytes stored
twice are one artifact.

Storing gives no custody. Custody is the signed
`ArtifactCustodyRecordedV1`, prepared as the lifecycle action
`{"action": "record_custody", "artifact_digest": hex}` (`Tasks.Lifecycle`).
Its actor is principal and grant only, since custody predates lifecycle
versions.

## Verification

- **`LifecycleTest`:**
  - custody is refused before the bytes are stored, and recorded after;
  - storing needs a grant in this project, a digest a task names, the right
    hash and at most the limit.
- **`SpruceGoose.Web.UploadTest`:**
  - stored over HTTP, then custody signed by the device;
  - refusals: no session, no grant, a digest no task names, wrong hash,
    malformed hash, wrong
    content type, a body over 8 MiB, a malformed digest in the action.
- **Node:** `nextStep` gives the digest to upload for a missing SOP or
  input, and none when the task waits on people.
- **Browser (Chromium):** in the end-to-end test:
  1. a wrong file is refused with nothing stored;
  2. the SOP is uploaded and its custody signed;
  3. the SOP is acknowledged and the task queued;
  4. the input is uploaded and its custody signed;
  5. the task is marked ready.

  The ledger holds both receipts, by the person's principal, for exactly
  those files.
- **Mutation:** if the server prepares custody for a different digest, the
  page refuses to sign and the browser test fails.

## Limits

- Files are at most 8 MiB, the custody limit.
- In a cluster, every node must mount the same artifact directory; see
  [Cluster](2026-10-19-cluster.md).
- A file no task names cannot be stored. A digest named and later replaced
  by a new readiness definition stays stored; nothing is deleted.
