# Editing a suggestion before accepting it

Date: 2026-10-19. Status: **implemented**. Follows
[deciding on suggestions](2026-10-18-decide.md).

## Decision

A person can now edit a pending suggestion and accept it as edited. The
ledger already supported this; the web view and the command contract now
offer it.

| Suggestion | What can be edited | Command |
| --- | --- | --- |
| timing | the timing (schedule and due time) | `TaskTimingRevisedV1` |
| create | title, description, timing | `TaskCreatedV1` |

The command still cites the suggestion (`suggestion_event_id`), so it
resolves the suggestion as any acceptance does. The ledger compares the
command's fields with the suggestion's (`Tasks.Timing`):

- equal: `accepted`;
- different: `amended`.

So no ledger change was needed. Opening the editor and accepting without
changing anything is an ordinary acceptance.

## Contract

`Tasks.Decisions` gains `{:amend, suggestion_id, edits}`:

- `edits` is a non-empty map of the suggestion kind's own fields (above).
  Any other key, or an empty map, is `:bad_amendment`.
- The command is built exactly as for accepting, with the edits in place of
  the suggestion's values. Fields not edited keep the suggestion's values.
- Whether an edited value is valid is the ledger's to say, before anyone
  signs:
  - a refused timing comes back as `invalid_timing`;
  - an empty title comes back as `empty_field`.

```
POST /api/v1/chapters/:c/tenants/:t/projects/:p/commands
     {"decision": "amend", "suggestion_event_id", "key_id", "edits": {"timing": …}}
```

The rest is the decision flow as before: the command is held for the
principal, signed on the person's device and submitted through
`/api/v1/commands/:id`.

## The web view

Each pending suggestion has **Edit…** next to Accept and Decline. It opens a
form filled from the suggestion:

- **Create suggestions:** title and description.
- **Schedule:** unscheduled, at a time (start and end, in the browser's
  local time), or all day (first and last day).
- **Due time:** optional.

The form's conversions are pure functions in `view.js`, `timingForm/1` and
`formTiming/3`:

- **All-day dates:** the form shows the last day; the ledger's end date is
  the day after it.
- **Time zone:** a timed schedule keeps the suggestion's time zone, or takes
  the browser's.
- **Untouched timing:** it is passed through exactly as suggested, seconds
  included, so editing only a title does not amend the timing.

**Review and sign** goes through the same path as every decision:

1. the page decodes what the server prepared;
2. it signs only if the command cites the suggestion and carries exactly the
   values entered (`device.same/2` compares deeply; CBOR integers may decode
   as BigInts);
3. it shows the command for confirmation.

## Verification

- **`CommandsTest` (ledger):**
  - an edited timing revises the task and resolves the suggestion as
    `amended`;
  - an edited title creates the task under it and keeps the suggested
    timing;
  - an edit equal to the suggestion is `accepted`;
  - other fields, an empty edit and an invalid timing are refused before
    signing, and the suggestion stays pending.
- **`SpruceGoose.Web.CommandTest`:** `amend` over HTTP, with `bad_amendment`,
  `bad_decision` and `invalid_timing` refusals.
- **Node:**
  - the form round-trips timed, all-day and unscheduled timings, in two
    time zones;
  - an untouched form keeps a second-precise timing exactly;
  - the page signs an amended command only with exactly the timing entered,
    whether its integers decode as numbers or BigInts.
- **Browser (Chromium):** the device accepts one suggestion, then edits a
  create suggestion's title and accepts it. The ledger holds a
  `TaskCreatedV1` with the new title, signed by the browser's key, and the
  suggestion is `amended`.
- **Mutation:** if the server ignores the edits, the page refuses to sign
  and the browser test fails.

## Not yet

- Editing a delegated agent's limits, or a task after it is created, from
  the view.
