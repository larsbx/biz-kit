# Postfix business email automation roadmap

## Decision

Build a self-operated business mail platform around **Postfix**, while
automating routine operations and keeping production cutover human-gated.
Postfix is the SMTP transport; it is not, by itself, a complete mail service.

The reference stack is:

- Postfix for SMTP receipt, authenticated submission, and delivery routing.
- Dovecot for IMAP, Maildir storage, authentication, quotas, and LMTP delivery.
- Rspamd with Redis for spam scoring, DKIM signing, DMARC evaluation, and rate
  controls.
- Thunderbird as the supported desktop client; mobile devices use their native
  IMAP/SMTP clients. A webmail component is optional and admitted separately.
- ACME-managed TLS certificates, DNSSEC where the domain provider supports it,
  and MTA-STS/TLS-RPT after the basic mail path is proven.
- Declarative host configuration, systemd supervision, encrypted backups, and
  executable contract tests. Secrets and mailbox data never enter Git.

This roadmap governs planning and automation. It does **not** authorize DNS
changes, opening public ports, credential creation, migration, or production
cutover.

## Non-negotiable preflight gate

Direct internet mail is blocked until every item below is proven:

- A dedicated static public IP has clean reputation, forward-confirmed reverse
  DNS, and operator-controlled PTR naming.
- The provider permits inbound and outbound TCP 25; clients use 587 with
  STARTTLS and authentication; IMAP uses 993 with TLS.
- Each sending domain has operator-controlled DNS and supports MX, SPF, DKIM,
  DMARC, CAA, MTA-STS, and TLS-RPT records.
- An off-host secondary access and recovery path exists for DNS, backups, and
  emergency communication.
- Legal retention, deletion, employee access, and incident-notification rules
  are recorded for each business.

Failure of any infrastructure item blocks direct delivery. The recovery path
is an explicitly approved SMTP relay for outbound mail or a managed mail
service; automation must never silently switch routes.

## Target architecture and boundaries

```text
Internet SMTP -> firewall/NAT -> Postfix :25 -> Rspamd -> Dovecot LMTP -> Maildir
Users --------> Postfix :587 (TLS + auth)            Thunderbird/mobile
Users ---------------------------------> Dovecot :993 (TLS + auth) --------^

Automation -> declared config -> preflight tests -> staged rollout -> monitors
Backups ----> encrypted off-host copy -> scheduled restore drill
```

- Public exposure is limited to 25, 587, and 993. Datastores and admin
  interfaces remain unexposed.
- Submission requires TLS and authentication. Port 25 never offers arbitrary
  authenticated relaying.
- Virtual domains, users, aliases, and quotas come from one declared account
  inventory; generated Postfix and Dovecot views must agree before reload.
- Mailbox data, DKIM private keys, TLS account keys, password hashes, recovery
  codes, backup keys, and provider credentials remain host-side secret state.
- Every reload is preceded by syntax, permission, routing, and anti-open-relay
  checks. Failed checks preserve the last known-good configuration.

## Automation roadmap

### Phase 0 — requirements and feasibility

Record domains, users, shared addresses, aliases, mailbox quotas, retention,
mobile/desktop clients, expected daily volume, maximum outage, and recovery
objectives. Probe port 25, PTR control, IP reputation, and DNS API capability.

Acceptance gate:

- Domain/user inventory is reviewed by a human.
- Direct-delivery preflight is reproducible and passes, or the roadmap records
  the approved relay/managed fallback.
- RPO, RTO, retention, and restore-test frequency are explicit.

### Phase 1 — reproducible lab

Build the full stack on non-production names and synthetic mailboxes. Pin
packages or container images to reviewed versions/digests. Generate secrets
host-side with refusal to overwrite existing values. Keep services under
systemd and keep state in dedicated, least-privilege stores.

Automate contract tests for:

- no open relay, no plaintext authentication, and no unexpected public ports;
- correct Postfix, Dovecot, and Rspamd syntax and permissions;
- SMTP submission and IMAP login using synthetic accounts;
- inbound delivery, outbound delivery, bounce handling, quotas, aliases, and
  catch-all refusal;
- DKIM signing, SPF/DMARC alignment, TLS, and abuse-rate limits;
- a positive and negative test for every fail-closed gate.

### Phase 2 — DNS and identity automation

Create an idempotent DNS plan that renders proposed records and diffs live DNS
before any mutation. Separate plan and apply. Apply requires human approval
and a rollback set.

Automate:

- MX, SPF, DKIM selectors, DMARC reporting, CAA, MTA-STS, and TLS-RPT checks;
- DKIM rotation with overlapping old/new selectors and delayed retirement;
- certificate issue/renewal with post-renewal service reload and TLS probe;
- account lifecycle: create, disable, alias, quota, password reset, and audit;
- configuration generation from the reviewed domain/user inventory.

### Phase 3 — observability and deliverability

Collect structured service logs without storing message bodies or credentials.
Alert on queue age/depth, repeated authentication failures, disk/inode pressure,
certificate expiry, DNS drift, DKIM/SPF/DMARC failure, backup failure, blocklist
appearance, and abnormal outbound volume.

Daily automation may inspect and report. It may retry safe idempotent checks,
but it may not delete queues, rotate identity keys, alter DNS, unblock accounts,
or change delivery routes without an admitted task and human approval.

### Phase 4 — backup and recovery

Back up mailboxes, account inventory, Postfix/Dovecot/Rspamd configuration,
DKIM material, and the minimum metadata needed for reconstruction. Encrypt
before leaving the host and retain at least one off-host copy.

Prove recovery by restoring into an isolated environment, verifying mailbox
counts and sampled hashes, logging in over IMAP, and sending synthetic mail
through the restored stack. A backup without a successful restore drill is
reported as unverified.

### Phase 5 — staged migration and cutover

Lower DNS TTLs only after the lab and recovery gates pass. Pre-seed mailboxes,
run an incremental sync, pilot one non-critical domain/user cohort, and hold a
rollback window. Change MX only with approval; keep the former service able to
receive mail during the agreed overlap. Reconcile final mailbox counts and
message samples before retiring the former path.

### Phase 6 — routine operations

Schedule configuration drift checks, certificate and DNS checks, queue and
reputation reports, encrypted backups, and restore drills. Upgrade in a lab,
run the full contract suite, canary one domain or synthetic account, then
promote. Every upgrade retains a tested rollback path and last known-good
configuration.

## Client standard

- Thunderbird receives an organization profile for IMAP 993/TLS, SMTP
  submission 587/STARTTLS, server-name validation, and no plaintext fallback.
- Autoconfig/autodiscover files are generated from the same domain inventory
  and tested against synthetic accounts.
- Shared role addresses such as `billing@`, `support@`, and `accounts@` are
  aliases or shared mailboxes with named-user access; users do not share a
  master password.
- MFA for IMAP/SMTP requires a deliberately selected authentication layer or
  app-password design. Password-only authentication is an explicit residual
  risk until that phase is implemented.

## Twelve-Factor review

Postfix and Dovecot are stateful infrastructure, so the factors are a delivery
baseline rather than a complete architecture:

- One version-controlled source declares configuration and automation; secrets
  remain environment/credential inputs.
- Dependencies and versions are pinned; build, release, and run are distinct.
- Mailboxes, queues, Redis, and account data are attached state/backing
  services, not disposable process state.
- Processes are supervised, restartable, and disposable without losing
  durable mail; services bind explicit ports.
- Development uses synthetic data but maintains configuration parity with
  production.
- Logs are event streams consumed by host observability.
- Administrative jobs such as DKIM rotation, migration, and restore drills are
  one-off, auditable processes.

Deliberate deviations: mail delivery cannot be stateless, local queueing is
required for SMTP semantics, and production DNS/IP reputation cannot be made
fully equivalent in a lab. Those deviations require stronger backup, replay,
staging, and external-delivery probes.

## Completion criteria

The implementation program is ready for production consideration only when:

- all preflight and contract tests pass in the lab;
- DNS changes have a reviewed plan, rollback, and propagation proof;
- a synthetic external round trip succeeds in both directions without relay;
- Thunderbird and mobile client profiles pass login/send/receive tests;
- monitoring produces a known-positive alert and clears it correctly;
- an isolated restore drill meets the declared RPO/RTO;
- a pilot migration reconciles counts and sampled content;
- an operator can follow a written recovery runbook without hidden knowledge;
- the final production cutover is separately admitted and explicitly approved.
