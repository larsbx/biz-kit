# Hermes assistant admin runbook

For the client's internal admin. Part of [[24.12 Hermes assistant on-site deployment]].

## What you own

You run four jobs: adding people, removing people, rotating keys, and restoring
files. Anything that changes the cloud zone itself goes to the support contact.
Fill the blanks during handoff.

For the add/revoke handoff test, you perform the client-side steps using this
runbook, including the request to the support contact. The support contact
regenerates the topology/configs and handles the cloud edge.

## Add an employee

About 30 minutes, plus the support contact's config round trip. Don't call it
done until steps 6–9 pass.

1. Record name, job role, department(s), Buzz account, Telegram account, any
   extra channel, and machine role (`anchor`, `desktop`, or `laptop`) in the
   roster. For an anchor, record whether it is the librarian.
2. Clone the base Hermes profile; name it after the employee; set role-specific
   use cases.
3. Create their Buzz hub account and add them to their team's threads. Then
   have them open the Telegram bot and tap Start. Add their Telegram
   user ID to that profile's allowlist on the gateway. Confirm the catch-all
   route still catches unknown senders.
4. Extra channel only if the roster asks for one: add their WhatsApp number or
   SMS number to the same profile's allowlist.
5. Run the signed Windows installer on their machine; join it to the tailnet;
   check its approved Tailscale ACL tag. Record and send its tailnet hostname,
   Syncthing device ID, machine role, department(s), and librarian designation
   (for an anchor) to the support contact. Install the generated office configs
   on this machine and every affected office peer they list, with Syncthing
   stopped, preserving each device's own keys; then restart. The support contact
   installs, restarts, and verifies any affected cloud-edge config, per
   [[24.12f Hermes assistant office file plane]].
6. Test: send a Telegram message, get a reply (round-trip); post once in the
   Buzz hub and confirm their agent can see it.
7. Test: send a document via the upload link; confirm it appears in Buzz and
   the librarian files it in the correct tier.
8. Test: send a restricted doc in chat; confirm it is refused and redirected to
   the upload link.
9. Test folders and send/receive modes against `matrix.md`: a non-anchor gets
   company-wide folders and only its assigned departments' open/internal
   folders; laptops receive only. An anchor holds every department, restricted
   folders inside its vault; only the librarian anchor shares intake with the
   edge. Use the handoff checks in [[24.12f Hermes assistant office file plane]].
10. Hand over the quick card; log the date in the roster.

## Remove an employee

Do this on their last day, before they leave the building. Order matters: cut
access first, clean up second. Arrange the support contact's updated configs
before the planned cutoff. Use the device-cutoff steps immediately for a lost
device too.

1. Remove their Telegram user ID, and any WhatsApp or SMS number, from the
   profile allowlist on the gateway. Deactivate their Buzz hub account.
2. Disable their Hermes profile. Archive it; don't delete it until the owner
   says so.
3. Cut Syncthing access for every one of their devices using **Remove a device**
   in [[24.12f Hermes assistant office file plane]]: stop affected surviving
   office peers, install their regenerated configs, and verify the departing
   IDs are absent from device and folder-sharing lists with no active
   connections. Require the support contact to stop, update, restart, and
   verify the affected cloud edge, including its generated deployment source;
   obtain their confirmation that it is updated and checked or isolated.
   Keep offline office peers isolated from LAN and tailnet until updated;
   keep sync stopped if configs are delayed. Confirm every affected office
   peer and the support-managed edge is updated and checked or isolated
   before continuing.
4. Remove each departing machine from the tailnet (Tailscale admin console →
   Machines → Remove). Tailnet removal alone is not the Syncthing cutoff:
   office peers also accept connections over the LAN.
5. Revoke any personal upload links issued to them.
6. If they knew a vault key or shared secret, rotate it now (see Rotate keys).
7. Verify: a message from their Telegram account gets no profile reply
   (catch-all only); tailnet access is gone. With a test device, confirm
   Syncthing cannot sync over either LAN or tailnet. For a lost device, retain
   peer-side removal and isolation evidence instead.
8. Log the cutoff time, affected-peer checks, any isolated peers awaiting
   update, and who verified in the roster. Do not resume an isolated peer until
   its generated config is installed and checked. Files already on a departed
   device are not erased by revocation.

## Rotate keys

Rotate on schedule, and immediately when someone who knew a key leaves or a
device is lost.

| Secret | Schedule | Who | Steps |
| --- | --- | --- | --- |
| Vault key | Yearly + on key-holder exit | Admin + one other key holder | Generate new key → re-encrypt vault → confirm a restricted file opens → destroy old key → update holder list |
| Upload links | Quarterly + on leak | Admin | Issue new links per tier → send new quick cards → revoke old links → test one upload per tier |
| Tailscale auth keys | Before each new enrollment (one-time keys) | Admin | Generate a one-time, tagged key per machine; never reuse |
| Telegram bot token | Yearly + on leak | Support contact | Escalate; don't rotate alone |
| Buzz hub admin / agent credentials | Yearly + on admin exit | Support contact | Escalate; don't rotate alone |
| Gateway / WhatsApp / SMS credentials | Yearly, or on bridge re-link | Support contact | Escalate; don't rotate alone |
| Syncthing device IDs | On device loss | Admin + support contact | Apply the peer-side cutoff in [[24.12f Hermes assistant office file plane]] before tailnet removal; re-enroll only a rebuilt machine with a new ID |

After any rotation: run one Telegram round-trip and one upload test, then log

## Restore from backup

Restore to a new location first, never on top of live files. Check it, then
swap.

**One file or folder (you can do this)**

1. Find the J.D number of what's missing (e.g. `21.04`).
2. Open the backup for the most recent good date; restore that path to a
   `_restore/` folder on an anchor.
3. Open the file to confirm it's intact; restricted files must still be
   encrypted.
4. Move it into place; Syncthing spreads it to the other machines.
5. Note what was restored, from which date, and why.

**Lost anchor machine (you can do this)**

1. Apply the lost-device cutoff above for the old Syncthing ID. Then rebuild
   the machine; run the installer; join the tailnet with a fresh one-time key.
2. Mount the vault, then install the anchor config from the support contact
   (send the new Syncthing ID, hostname, `anchor` role, department(s), and
   librarian designation; other devices get updated configs too); let it
   resync from the other anchor. The support contact handles and verifies any
   affected cloud-edge update.
3. If no other anchor exists, restore the full office share from backup
   instead.

**Office zone down or vault damaged (escalate)**

Call the support contact. Have ready: what failed, when, the last good backup
date, and both vault key holders on hand.

## Routine checks

**Weekly (10 min)**

- [ ] Backup job ran and succeeded every day this week
- [ ] Buzz intake: nothing stuck unrouted or unfiled
- [ ] Syncthing: all anchors "Up to Date", no conflict files
- [ ] Disk space on anchors above 20% free
- [ ] Send one test message on Telegram, one post in the Buzz hub, and one on each extra channel in use

**Monthly (30 min)**

- [ ] Restore one random file to `_restore/` and open it
- [ ] Tailnet machine list matches the roster; remove anything unknown
- [ ] Gateway allowlists and Buzz hub accounts match the roster; no leavers left on them
- [ ] Syncthing device list matches the roster; nothing pending or unknown
- [ ] Check rotation dates in Rotate keys; do any that are due

## Troubleshooting + escalation

| Symptom | Likely cause | First fix | Escalate if |
| --- | --- | --- | --- |
| Nobody gets Telegram replies | Gateway down or bot token revoked | Check the gateway status; tell staff to reach their agent through the Buzz hub meanwhile | Still down after 1 hour |
| Buzz hub unreachable | Hub down or cloud zone unreachable | Nothing new is routed or filed; tell staff to hold documents until it's back | Still down after 30 minutes |
| Message or document never shows up in Buzz | Sender not on an allowlist, or upload link not wired to Buzz | Check the sender's allowlist; test the link yourself | It happens for an enrolled sender with the right link |
| WhatsApp users get no replies | Baileys bridge dropped or number unlinked | Tell them to use Telegram now; re-link the bridge if you've been shown how | Still down after 1 hour, or the number is banned |
| One person gets no replies | Telegram user ID missing from allowlist, or profile disabled | Check the allowlist and profile status | Allowlist is correct and it still fails |
| Document filed in the wrong tier | Wrong upload link used, or librarian misfiled it | Move the file; resend that person's quick card | It happens with the right link |
| Restricted doc accepted in chat | Refusal rule broken | Delete the message and file; tell the owner | Always: escalate the same day |
| Machine can't reach office files | Tailscale logged out or ACL tag wrong | Reconnect Tailscale; check the machine's tag | Tag is correct and it still fails |
| A department's files missing on a machine | Device not in that department, or an old config | Compare with the company's folder matrix; ask the support contact for updated configs | Config is current and it still fails |
| Syncthing conflict files | Same file edited on two machines | Keep the newer copy; delete the `.sync-conflict` file | Conflicts keep coming back |
| Backup job failed | Disk full or cloud zone unreachable | Free space; re-run the job | Fails two days in a row |

When you escalate, send: what broke, when it started, who's affected, and what
you already tried.
