# AgentCore — agent-agnostic execution contracts

This is a **dependency-free**, execution-engine-independent library. It does
not load Hermes, Pi, OpenShell, a particular model SDK, or any agent provider.

It provides two small contracts:

- `AgentCore.ExecutionPort`: an asynchronous adapter interface:
  `launch(execution, approved_profile, effect_id)`, `poll(handle)`,
  `cancel(handle, reason)`. Adapters can be hosted/remote agents, local
  processes, sandbox environments, queue workers or other engines.
- `AgentCore.Profiles.resolve(run, registry, hash_manifest)`: matches an
  engine-neutral signed `execution_profile_id` and immutable
  `execution_profile_digest` against an administrator-approved registry.
  It hashes the **full execution manifest** and binds the selected adapter
  module by its declared identity; silent policy or adapter replacement is
  rejected. The host provides the canonical hash implementation (biz-kit
  uses CoopSubstrate.Canonical.hash!/1).

No `run` map generated by an agent may supply a module name, command, model,
network policy or deployment URL. The host-controlled registry maps a profile
ID to a known adapter module, while the signed profile digest binds its
versioned, declarative configuration. The manifest has three required
properties plus an adapter identity:

```elixir
%{
  "id" => "example-profile",
  "version" => 1,
  "adapter_module" => "Elixir.YourReviewedAdapter",
  "parameters" => %{"option" => "reviewed-value"}
}
```

The example is a configuration shape, **not a default allow policy**.
Administrator admission, versioning, immutable publication, secret-handling
and profile-approval registry operations remain to be implemented in
issue #92. Adapter modules must be known and reviewed by the host; do not
map `adapter_module` strings to atoms dynamically.

AgentCore owns neither TaskCore state nor authorization nor an agent loop.
A request is not executable until the coordinating host independently
authenticates and authorizes the task-read and run permissions, verifies
the current signed intent, resolves the approved execution profile, checks
runtime capabilities and the current privacy/consent policy, and acquires
a durable idempotent launch lease.

A successful adapter poll is **not** a task completion or custody receipt.
Every tool invocation and business action must independently satisfy current
domain authority. For cancellation, `:ok` only means that the adapter accepted
the cancellation request; an operational reconciler must confirm termination.

## Validation

```sh
cd apps/agent_core
mix test
```

The fake adapters in `test/profiles_test.exs` are deliberately unrelated:
one represents a sandboxed worker and another a hosted service. This tests
engine-neutral selection, signed-profile digest drift, adapter identity
replacement and fail-closed behavior, **not** actual execution infrastructure.

See [signed run intent architecture](../../docs/architecture/2026-10-24-signed-agent-runs.md).

## Engine-neutral preflight and operational attempt rules (new slice)

`AgentCore.Capabilities.check/2` rejects missing or unsupported features,
data classes, regions, duration and output ceilings. Requirements must be
computed by the trusted coordinating host; profile declarations do not
independently prove physical residency or isolation.

`AgentCore.Preflight.prepare/4` ties the signed TaskCore run version and
profile digest to capabilities and exact resource bounds. It creates a
uniform execution description and deterministic effect ID, without starting
an agent or conferring any read/write authority.

`AgentCore.Attempts` adds a pure operational state machine for registering a
stable signed effect, lease claiming and renewal, epoch/token fencing,
non-authoritative candidate digests, cancellation requests, and *explicit*
backend reconciliation of uncertain expired attempts. Expiration alone never
permits a duplicate launch: a backend must prove absence or recover an
already-produced result first.

**No durable dispatcher has been built.** A production host must persist each
state transition with a transactional compare-and-swap, protect lease tokens,
recheck signed ledger authority and user consent at each critical boundary,
provide idempotent backend launch using the same effect ID, and reconcile
external execution handles. In-memory tests do not demonstrate crash-safe
storage, mutual exclusion across nodes, real cancellation, or admissible
business effects.
